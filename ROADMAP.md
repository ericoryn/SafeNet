# SafeNet KZ — план внедрения

Это последовательность работ с критериями перехода, без обещанных сроков и заранее назначенных показателей. Текущая система помогает ручной проверке. Результаты синтетического теста находятся в [метриках](reports/METRICS.md); полнота казино выросла до 33,3% на повторном test, но остаётся недостаточной для заявления о готовности к реальному мониторингу.

## 1. Закрыть пробелы качества до пилота

Сохранить первый test как опубликованный результат. Разбирать ошибки на train/validation, расширять словари по независимым источникам и требованиям, добавлять трудные негативы. После изменения правил прежний test использовать как регрессионный; для новой независимой оценки собрать новый, заранее закрытый набор с отдельными семействами и кампаниями. Не объявлять повторную проверку того же набора независимой.

Критерий перехода: все три трека имеют измеримые precision/recall/FPR, согласованы ограничения на ложные тревоги и пропуски, есть результаты отдельно для RU/KK, транслита, смешанного текста и OCR. Целевые значения утверждаются владельцем пилота; сейчас они не согласованы.

## 2. Пилот с модераторами

Ограниченная группа аналитиков, отдельная база и доступ по ролям; фиксированный объём материалов и возможность остановить импорт. Решение остаётся за человеком. Измерять время разбора, долю спорных решений, полезность объяснений, пропущенные случаи и ложные тревоги. Организовать повторную разметку спорных примеров вторым аналитиком.

До подключения реальных источников нужны согласование владельца данных, разрешённый способ получения, условия платформы, срок хранения и порядок удаления. Закрытые группы и приватные архивы автоматически не собираются.

## 3. Обратная связь и улучшение правил

Действия уже сохраняются с версией результата. `python tools/feedback.py --input export.jsonl --output feedback.jsonl` принимает только завершённый экспорт, выбирает последнее решение и исключает устаревшие версии и «Запросить проверку».

«Подтвердить признаки» даёт общую положительную метку; треки должен уточнить разметчик. Скрипт не превращает её в три положительных метки. «Ложное срабатывание» даёт отрицательные метки треков. Перед обучением: проверка разметки, группировка по кампании, изоляция train/validation/test, фиксация версии и порогов. Для текущих взвешенных правил улучшение означает пересмотр правил/весов и калибровку, а не обучение отсутствующей ML-модели.

Автоматически менять работающие оценки по нажатию кнопки нельзя: кандидат сравнивается с закреплённой версией, затем публикуется с возможностью отката. Нынешний экспорт — подготовка обратной связи; автоматическое переобучение не включено.

## 4. Поток и масштабирование

Текущая реализация: один владелец SQLite, ограниченная долговременная очередь, кэш безопасной подготовки, пакетный импорт, отдельный OCR с дедлайном. Сначала измерить реальные очереди и задержки. При исчерпании одного процесса: PostgreSQL и брокер, независимые OCR-работники, идемпотентный результат и ограничение нагрузки на каждого заказчика.

Текстовые правила — дешёвый первый этап. В MVP нет дорогой ML-модели, поэтому дополнительный фильтр не отбрасывает скриншоты до OCR: иначе текст в изображении будет потерян. Если добавится классификатор/эмбеддинги, запускать его только по измеренному порогу кандидатов, отдельно проверяя потерю полноты. ASR остаётся опцией; готовые транскрипты уже поддерживаются.

## 5. Мониторинг

Наблюдать размеры очереди, failed/incomplete, ошибки OCR, задержки p50/p95, объём БД и перезапуски. Контролировать распределение языков, источников, баллов и решений. Дрейф сигнала не равен падению точности: его подтверждают свежей размеченной выборкой.

Для каждой версии хранить конфигурацию, хеш кода, состав и разбиение набора, отчёт метрик, дату и ответственного за публикацию. При ухудшении или сбое возвращать предыдущую версию; решения аналитиков и исторические результаты сохранять.
